Implement Azure Security — Managed Identities, Key Vault, and RBAC

2024-03-01 Azure Security Azure Developer Associate

Security in Azure applications centres on three main areas: who can access resources (identity and RBAC), what secrets the application uses (Key Vault), and how services authenticate to each other without storing credentials (managed identities). This post covers the concepts that appear most frequently in the Developer Associate exam.

Microsoft Entra ID (formerly Azure AD)

Microsoft Entra ID is the cloud identity platform that underpins authentication and authorisation across all Azure services. Applications registered in Entra ID receive a service principal — an identity used to authenticate and obtain access tokens for Azure resources.

App registration vs service principal

  • An app registration defines the application identity globally in the Entra ID tenant
  • A service principal is the local representation of that registration in a specific tenant
  • When you register an app, an enterprise application (service principal) is automatically created in the same tenant

OAuth 2.0 flows relevant to developers

  • Authorization code flow — for web apps with a browser; user signs in, app receives a code, exchanges it for a token
  • Client credentials flow — for service-to-service calls; no user involved; app authenticates with a secret or certificate
  • On-behalf-of flow — a service receives a user token and exchanges it for a token to call a downstream API on behalf of that user
  • Device code flow — for CLI tools and devices without a browser

Managed Identities

A managed identity gives an Azure resource (a VM, App Service, Function App, AKS pod, etc.) an automatically managed identity in Entra ID. The key benefit is that you never store credentials — Azure manages the secret rotation and token issuance.

System-assigned vs user-assigned

  • System-assigned — tied to a single resource; created and deleted with that resource; simple to set up
  • User-assigned — an independent resource that can be assigned to multiple services; useful when several resources need the same access, or when you need the identity to outlive a single resource

How it works in practice

  • Enable managed identity on the resource (one toggle in the portal or one CLI flag)
  • Assign the identity an RBAC role on the target resource (e.g. Storage Blob Data Reader on a storage account)
  • In application code, use DefaultAzureCredential from the Azure Identity SDK — it automatically uses the managed identity token when running in Azure
  • Locally, DefaultAzureCredential falls back to your developer credentials (Azure CLI login), so no code change is needed between local and deployed environments

Azure Key Vault

Key Vault is the centralised secrets management service. It stores three types of objects: secrets, keys, and certificates.

Secrets

  • Store connection strings, API keys, passwords, and any other sensitive string values
  • Versioned — each update creates a new version; previous versions remain accessible until explicitly deleted
  • Soft delete is enabled by default and protects against accidental deletion (configurable retention period)

Keys

  • Cryptographic keys for encryption, signing, and wrapping operations
  • Can be software-protected or HSM-protected (hardware security module — requires Premium tier)
  • Used by services like Storage (customer-managed keys) and Disk Encryption

Certificates

  • Key Vault can manage the full certificate lifecycle including auto-renewal with DigiCert and GlobalSign
  • When a certificate is stored, Key Vault also stores the private key as a Key Vault Key and the certificate data as a Secret

Accessing Key Vault from application code

  • Use the SecretClient from the azure-keyvault-secrets SDK
  • Authenticate with DefaultAzureCredential — no secrets needed in code
  • In App Service and Azure Functions, use Key Vault references in app settings: @Microsoft.KeyVault(SecretUri=https://vault.vault.azure.net/secrets/name/version)
  • The app's managed identity must have the Key Vault Secrets User role (or the legacy access policy equivalent)

Role-Based Access Control (RBAC)

Azure RBAC controls who can do what on which Azure resource. A role assignment has three parts: a security principal (who), a role definition (what actions), and a scope (which resource or resource group).

Built-in roles to know

  • Owner — full access including ability to assign roles
  • Contributor — full access to resources, cannot assign roles
  • Reader — read-only access
  • Storage Blob Data Contributor — read/write/delete access to blob data (not storage account management)
  • Key Vault Secrets User — read secrets from Key Vault
  • Key Vault Secrets Officer — manage secrets (create, update, delete)
  • AcrPull — pull images from Azure Container Registry

RBAC roles control the management plane (Azure Resource Manager operations). For data plane access (reading blobs, reading secrets), use the appropriate data-plane roles or access policies rather than relying on Owner/Contributor.

Microsoft Authentication Library (MSAL)

MSAL is the library used to acquire tokens from Entra ID in application code. It handles token caching, refresh, and the details of each OAuth flow.

  • For apps running on Azure, prefer DefaultAzureCredential (Azure Identity SDK) which handles managed identities automatically
  • For apps that authenticate on behalf of a user (web apps, SPAs), use MSAL with the appropriate flow for the client type
